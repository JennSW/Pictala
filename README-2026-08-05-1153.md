## 3. Fixed the real timezone defect (closes #6)

`matcher.py` compared checklist and photo timestamps as naive
datetimes — a camera whose clock wasn't updated while traveling (e.g.
still on Pacific time during a trip) could silently land outside the match
window or even the wrong calendar day.

Pulled real EXIF data before designing anything and found the camera
(Sony ILCE-7M4) reliably writes an `OffsetTimeOriginal` tag per photo —
Flickr just doesn't expose it through the normal photo-list call, only
a separate per-photo lookup. Built on that instead of guessing:

- New `Photo.utc_offset` column, backfilled lazily during sync (not
  re-fetched once cached).
- Expected offset derived from the **checklist's own GPS coordinates**
  (`timezonefinder` + `zoneinfo`, DST-correct) — never a hardcoded home
  timezone, so a trip stays in destination-local terms throughout,
  no day-boundary bugs from timezone conversion.
- Mismatches surface as a warning on the photo card with an **Adjust**
  action that corrects `date_taken` via real datetime math (so a
  correction crossing midnight rolls to the right calendar day) and
  re-runs matching.

Verified live: simulated a mismatch on a real synced photo, confirmed
the warning rendered with the correct offsets, applied the correction,
confirmed the timestamp/offset updated and the warning cleared.

Known gap, not addressed: if a checklist's own date is wrong (e.g. a
Casual Observation logged well after the fact), no photo-side check
can catch that. The actual trip photos aren't synced
yet, so this is unverified against the real case that originally
motivated it — worth a check once they're uploaded.

### 6. Closed #8 by finding, not by tuning — folded into #9

Revisited #8 (distance cutoffs for large-area hotspots like Smith Island).
While investigating #6 I'd already found the real cause: the primary
camera (Sony ILCE-7M4) has no GPS receiver, so photo GPS is essentially
always absent (1 of 594 photos has coordinates, and even that one looks
manually placed on Flickr's map, not camera-captured). Since matcher.py's
distance check is skipped whenever coordinates are missing, the real
consequence is the *opposite* of the original worry: Smith Island's
same-day fallback currently applies **zero** spatial filtering, not a
too-tight one. Closed #8 with that finding; folded the actual remaining
risk (an unrelated same-day photo could get offered as a candidate for a
large-area checklist) into #9, since it's the same underlying shape as
the June 20 Tolt/Juanita disambiguation problem.

### 7. Built checklist-less photo clusters (closes #35)

The July 11 falconry photos (indoor/captive birds — permanently excluded
from eBird, confirmed by you directly: "this was an indoor photo session
with birds... they will never be uploaded to eBird") made #35 concrete.
Every part of the app required a checklist to show or identify a photo at
all, so these 55 photos plus 3 new same-day Juanita Bay Park morning
photos were completely invisible.

- Made `Match.checklist_id` nullable rather than using a sentinel like
  `0` — discussed the tradeoff directly: a real FK constraint already
  supports "no reference" cleanly, null can't be silently misread as a
  real checklist by code that forgets a special case, and critically, a
  checklist-less Match can later have `checklist_id` set in place once a
  real checklist shows up (e.g. if Juanita Bay Park gets a real eBird
  upload) — same row, no separate reconciliation table.
- New `photo_clusters.py` groups checklist-less photos by date +
  capture-time proximity (>60 min gap = new cluster) instead of GPS
  proximity from the original 7/28 design, since GPS is essentially never
  present.
- New "Photos not on eBird" section: lists clusters, lets you identify
  photos (Ask Claude or type a name), resolving against eBird's taxonomy
  or falling back to a plain note.
- Verified live: July 11 correctly split into 3 clusters (3 Juanita Bay
  Park photos, 1 timestamp outlier, 54 falconry photos). Ask Claude
  correctly identified a Eurasian Eagle-Owl (*Bubo bubo*) on a real
  falconry photo; confirmed `checklist_id` is actually `NULL` in the
  database afterward.

### 10. Batch "Ask Claude" (closes #5, also closes duplicate #22)

issue hoped for, not just fewer round trips.

### 12. Filed #45 — no client-side routing

You clicked a photo to view it larger, hit the browser's back button, and
landed on a fully reset BirdTrip page — lost which date/outing/cluster
you'd been in. Root cause confirmed: the app has no client-side routing
at all (no react-router, no URL params reflecting state) — every bit of
navigation state lives only in React state, so there's exactly one URL
for the whole app and back/reload has nothing real to return to except a
full remount. Filed as #45 with that diagnosis; real fix is routing with
URL-reflected state, a genuine lift (new dependency, restructuring how
detail views load), not scoped for immediate work.

### 13. Started #39, found the heuristic doesn't work, stopped

Phase-1 duplicate detection (issue #39): strip a trailing "copy"/"-N"
suffix from a photo's title, flag matches. Tested against real data
*before* wiring it into the API — first version flagged 499 of 594
photos, because this account's normal naming convention is itself
sequential dash-numbers ("June 7-1" through "June 7-26" are 26 real,
different photos) which is syntactically identical to the real duplicate
signature. Tightened the rule (only flag when the stripped base also
exists as its own separate real title, same day) and it was *still*
wrong: some days number sequentially starting unsuffixed ("June 8", "June
8-2", "June 8-3"...), so the tightened rule false-positived on those too.
Stopped there rather than ship a third guess under time pressure —
nothing was wired into any endpoint, so nothing is broken; the draft
`duplicate_detection.py` exists locally, uncommitted. Needs real examples
of both naming patterns to design a reliable rule — picking this up fresh
next session.
